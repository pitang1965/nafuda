# ADR-0029: 多言語対応のロケールはURLパスに含めず、Cookie＋Accept-Languageで決定する

- **ステータス**: 採用
- **決定日**: 2026-10-15
- **関連**: ADR-0027（印刷用ロックアップ）、ADR-0019（公開プロフィールはviewer-agnostic）

## 背景

英語・日本語の多言語対応（デフォルト：英語）を導入するにあたり、一般的なi18n実装では `/en/...` `/ja/...` のようにURLパスに言語を含める手法（Next.js の `next-intl` 等が典型）がよく使われる。

しかし、なふだは以下の**永続的なURL**を前提にした機能を複数持つ：

- プロフィールQR（`/u/{urlId}/p/{shareToken}`）— 印刷・インターネット公開前提の恒久URL
- イベントページ（`/e/{shareToken}`）
- [[印刷用ロックアップ]]（ADR-0027）— プロフィールQRをTシャツ・ステッカー等の**物理グッズに焼き込む**合成画像

これらのURLは一度印刷・配布されると書き換えができない。URLパスに言語プレフィックスを含める設計にすると、ロケール追加・変更のたびに既存の印刷物やブックマーク済みQRが指すURLの意味が変わる、あるいはリダイレクト処理が恒久的に必要になる。

## 問題

多言語対応のロケール決定・切り替えの仕組みをどう設計するか。特に、URL構造を変更しない制約の中で、どう自然な言語検出・切り替え体験を提供するか。

## 決定

**ロケールはURLパスに一切含めない。** 同一URLが閲覧者によって日本語にも英語にもなる（[[公開プロフィール]]がviewer-agnosticであるという既存原則 ADR-0019 と同じ発想で、「URL＝コンテンツの場所」と「表示言語＝閲覧者側の設定」を分離する）。

ロケールの決定は以下の優先順位で行う：

1. **Cookieに保存された明示選択**（手動切り替えUIで設定）があればそれを使う
2. なければ初回アクセス時に `Accept-Language` ヘッダーで自動判定（日本語なら日本語、それ以外は英語＝デフォルト）し、結果をCookieに保存する

アカウント（DB）には保存しない。ログイン状態・デバイスに関わらずCookie単位で完結する。

## 却下した代替案

- **URLパスにロケールを含める**（`/en/...`）: SEO的には有利だが、印刷済みQR・ロックアップの恒久URLと衝突する。今回の導入動機（訪日する知人に使ってもらう）はSEO訴求ではないため、この代償を払う理由がない。
- **ユーザーアカウントにロケール設定を保存**: 複数端末で言語設定を引き継げる利点はあるが、スキーマ変更・設定画面への導線整備が必要になり、今回のスコープ（コア導線＋周辺機能への翻訳適用）に対してオーバースペック。将来、他端末間の一貫性が問題になれば改めて検討する。
- **Accept-Languageのみで自動判定し、手動切り替えUIを持たない**: 訪日旅行者はブラウザの言語設定が必ずしも母語と一致しない（日本語学習中などの理由で日本語UIのままにしている等）ため、手動切り替えを用意しないと詰む可能性がある。

## トレードオフ

- **得るもの**: 既存の全ての永続URL（プロフィールQR・イベントURL・印刷用ロックアップ）がロケール導入後も無変更で動く。ロケール追加・削除が将来いつでもURL構造に影響せず行える。
- **失うもの／代償**: 言語ごとのURLが無いため、将来的に英語圏向けSEO（言語別インデックス）を狙う場合は別途対応が必要になる（今回は対象外と判断——ランディングページの多言語化自体を保留しているため影響なし）。同一URLでも閲覧者のCookieによって表示が変わるため、キャッシュ戦略（CDN/エッジキャッシュ）はCookieをキーに含めるか、UIチャンス文言をクライアント側でレンダーする設計にする必要がある（実装フェーズで要検討）。
