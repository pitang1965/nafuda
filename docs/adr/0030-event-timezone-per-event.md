# ADR-0030: イベントの開催タイムゾーンをイベント単位で記録する

- **ステータス**: 採用
- **決定日**: 2026-10-16
- **関連**: ADR-0029（多言語対応のロケール決定方式）、ADR-0020（チェックイン受付ゲート）

## 背景

英語・日本語の多言語対応（ADR-0029）の検討時点では、「出会い・イベントは常に日本国内」という前提のもと、[event.ts](../../src/server/functions/event.ts) の `buildEventDate` がフォーム入力を常に `+09:00`（JST）として解釈・保存し、`events` テーブルにタイムゾーン列も持たない設計のまま、英語表示では "JST" を固定で明記するだけで凌いでいた（海外開催イベント対応は別タスクとして見送り）。

その後、「海外在住の日本人や海外のファンダム・コミュニティが、日本国外でもなふだを使ってイベントを開催・交換する」というニーズが具体化し、海外開催イベント対応に着手することにした。

## 問題

イベント（企画イベント・即時イベント）の開催日時をどのタイムゾーンとして記録・表示するか。特に、企画イベント（事前にフォームで作成）と即時イベント（なふだ交換フロー中に自動作成、専用フォームを持たない）では取得できる情報が異なるため、両者で異なる取得方法が必要になる。

## 決定

`events` テーブルに IANA タイムゾーン ID（例: `Asia/Tokyo`、`Europe/London`）を保存する列を追加し、イベントごとに開催タイムゾーンを持たせる。

- **企画イベント**（`/events/new` で作成）: 作成者のブラウザのローカルタイムゾーン（`Intl.DateTimeFormat().resolvedOptions().timeZone`）を自動検出してフォームのデフォルト値にし、作成者が手動で変更できるセレクタを用意する。日付・時刻の入力はこの選択されたタイムゾーンのウォールクロックとして解釈する。
- **即時イベント**（なふだ交換フロー中に自動作成）: フォームを持たないため、作成時点のブラウザのローカルタイムゾーンをそのまま自動記録する（変更不可）。GPS 座標からの逆引きは行わない。
- 開催期間の開始・終了（`eventDate` / `eventEndDate`）は単一のタイムゾーンを共有する（開催中にタイムゾーンが変わる想定はしない）。
- この属性導入前に作成された既存イベント（タイムゾーン列が未設定）は `Asia/Tokyo` として解釈する（後方互換）。
- 表示は常に開催タイムゾーンの略称（`Intl` の `timeZoneName: "short"` で算出、例: JST・GMT+1）を日英どちらの表示でも明記する。閲覧者のブラウザのタイムゾーンへの変換表示は今回のスコープ外とする。

ADR-0020（チェックイン受付ゲート）の受付可否判定は常に絶対時刻（UTC インスタント）の比較であり、イベントのタイムゾーンが多様化しても判定ロジックへの影響はない。

## 却下した代替案

- **GPS 座標からタイムゾーンを逆引きする外部 API を導入する**: 端末のタイムゾーン設定がズレていても補正できる利点はあるが、新たな外部サービス依存を増やし、かつ現在 GPS 取得は任意（スキップ可能）のため、タイムゾーン決定の前提として必須化すると既存のUXを変えてしまう。スマートフォンは通常「自動的にタイムゾーンを設定」が有効で実際の所在地と一致することが多いため、ブラウザのローカルタイムゾーンで十分と判断した。
- **閲覧者のタイムゾーンへの変換表示を今回同時に導入する**: 海外の友人が自国時間で把握できる価値はあるが、「どちらの時刻がイベント開催地の正式な時刻か」を混乱させずに両方見せるUI設計が別途必要になり、スコープが膨らむ。今回は開催タイムゾーンの正しい記録・明記までに留める。
- **既存イベントのタイムゾーンを「不明」として扱う**: 実態と異なる上、過去イベントの表示が不自然になる。これまで全イベントが実質 JST で作成・解釈されてきた事実と一致する `Asia/Tokyo` への後方互換フォールバックを採用した。

## トレードオフ

- **得るもの**: 海外開催イベント（海外在住の日本人・海外ファンダムのオフ会等）でも、開催地の正しい時刻とタイムゾーンを記録・表示できる。ADR-0029 の多言語対応と組み合わさり、「訪日・訪外のどちらでも迷わず使える」という当初の目的に一歩近づく。
- **失うもの／代償**: 閲覧者のローカル時刻への変換が無いため、遠隔地の閲覧者は開催タイムゾーンの時刻を自分で読み替える必要がある（将来ニーズが具体化したら別途検討）。企画イベントのタイムゾーン手動変更を許すため、作成者が誤って不正確なタイムゾーンを選んでしまうリスクが生まれる（バリデーションやUI上の注意書きは実装フェーズで検討）。
